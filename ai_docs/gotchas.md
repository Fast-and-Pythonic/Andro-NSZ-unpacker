# Gotchas

Нетривиальные ловушки. Формат `G##` — стабильный якорь. Добавлять после отладки
> 30 мин с неочевидной причиной.

## G01: Общий batch-прогресс заполняется раньше, чем распакованы все файлы
**Симптом:** в режиме очереди overall-бар доходит до 100% задолго до того, как
последние файлы реально распакованы.
**Корень:** знаменатель считался один раз из размеров **сжатых** входных файлов,
а «сделано» накапливалось до размеров **распакованного** вывода (`fileTotals[i]`
подменяется на uncompressed-total, как только приходит первый прогресс файла).
Разные единицы → сумма «сделано» дотягивается до знаменателя слишком рано.
**Решение:** в `MainViewModel.emitOverall()` знаменатель пересчитывается
динамически из `fileTotals.sum()` (те же единицы, что и числитель). После цикла —
финальный emit на 100% (троттлинг иначе оставляет бар чуть ниже).
**Как заметить:** бар на 100%, а статус ещё «Распаковываем…» и файлы в очереди
не `Completed`. Режим папки этим не страдает: там «сделано» привязано к завершению
файлов по входным размерам (`structure.totalSize`).

## G02: Debug-сборка распаковывает в разы медленнее release
**Симптом:** конвертация в debug-APK мучительно медленная, в release — быстрая.
**Корень:** zstd как CMake-зависимость наследует `CMAKE_BUILD_TYPE=Debug` → `-O0`
+ `-DDEBUGLEVEL=1` (внутренние asserts). Декомпрессия — горячий путь.
**Решение:** в `CMakeLists.txt` `libzstd_static` принудительно собирается на
`-O3 -DNDEBUG -UDEBUGLEVEL -DDEBUGLEVEL=0` (см. [architecture.md](architecture.md)
A01). Не убирать это при правках CMake.
**Как заметить:** профиль показывает время в zstd-функциях; release-сборка той же
ревизии кратно быстрее.

## G03: Прямое чтение входа по fd падает на FUSE-storage
**Симптом:** конвертация некоторых файлов сразу падает на парсинге PFS0/NCZ, хотя
файл валидный; те же файлы из других источников работают.
**Корень:** FUSE-backed scoped storage отдаёт дескриптор, чей путь
`/proc/self/fd/<n>` натив не может переоткрыть. Поэтому вход передаётся как `"fd:N"`
(`dup()+fdopen()`), но и это иногда не проходит на парсинге.
**Решение:** в `NszConverter` есть откат: при `ERR_OPEN_INPUT/INVALID_PFS0/
INVALID_NCZ/IO` и активном `inputPfd` вход копируется в кэш и конвертация
повторяется (см. [architecture.md](architecture.md) A05–A06). Не удалять этот
ретрай.
**Как заметить:** в статус-логе строка «Direct read failed (code …), copying to
cache and retrying», после чего файл конвертируется успешно.

## G04: Язык приложения нельзя читать из DataStore
**Симптом:** при попытке хранить язык в DataStore локаль применяется с задержкой /
не применяется к первому кадру UI.
**Корень:** `MainActivity.attachBaseContext()` выполняется **синхронно до**
инициализации Compose и до доступности корутин, а DataStore асинхронный.
**Решение:** `language` хранится в **SharedPreferences** (синхронное чтение
`getLanguage()`), остальные настройки — в DataStore. Смена языка → `recreate()`.
См. [architecture.md](architecture.md) A08.
**Как заметить:** язык «прыгает» или применяется только после пересоздания Activity.

## G05: Выравнивание PFS0 нужно воспроизводить из исходника, а не угадывать
**Симптом:** распакованный NSP побитово совпадает с эталонным `nsz` для большинства
файлов, но для отдельных получается на ~32 КБ меньше (несовпадение SHA-256), хотя
все вложенные NCA идентичны.
**Корень:** официальные NSP выравнивают данные первого файла на `0x8000`, вставляя
ведущий зазор между таблицей строк и первым файлом. Эталонный `nsz` по умолчанию
(`fixPadding=False`) **сохраняет исходный зазор** = `entries[0].offset` из входа.
`pfs0_write_header` же вычислял зазор эвристикой «выравнивать, только если первым
идёт `.tik`/`.cert`». Когда выровненный контейнер начинался с `.cnmt.nca`, зазор
терялся → плотный, более короткий файл.
**Решение:** в [pfs0.c](../app/src/main/cpp/pfs0.c) `data_gap` берётся как
`files[0].data_offset - data_area_offset` (= исходный `entries[0].offset`).
Рename `.ncz`→`.nca` не меняет длину имён, поэтому размер заголовка/data-area
идентичен входу и зазор переносится напрямую. Это совпадает с дефолтом
`NszDecompressor.py` (`getFirstFileOffset()`). Эвристику `is_meta` не возвращать.
**Как заметить:** размер выхода меньше эталона ровно на `0x8000 − header_size`;
PFS0-парс показывает `entries[0].offset == 0` там, где в исходном `.nsz` он был
ненулевым. Тела NCA при этом совпадают (имя NCA = SHA-256 содержимого).

## G06: HFS0/XCI — выравнивание 0x8000 и нероундтрип полного XCI
**Симптом / ловушки** при доработке XCZ→XCI под эталон:
1. HFS0-заголовок раздела **не** выравнивается до 0x20 по строковой таблице (как
   PFS0). Вместо этого данные первого файла раздела кладутся на границу **0x8000**, а
   зазор кодируется в `entry.offset` (`0x8000 − header_size`) + добивается нулями.
   `string_table_size` в заголовке HFS0 — **сырая** длина, без паддинга. Это диктует
   `nsz.Fs.Hfs0.Hfs0Stream` (`headerSize = 0x8000`, `len(stringTable)`).
2. Поля `hashed_region_size` и `sha256_hash` в записях HFS0 — **всегда нули** (и у нас,
   и у эталона; это не баг, не «чинить»).
3. **Полный XCI (key area на 0x0, заголовок на 0x1000) эталон НЕ round-трипит:**
   `XciStream` всегда хранит лишь первые 0x200 и кладёт hfs0 на 0xF000, поэтому
   `.xcz`, сжатый из полного XCI, эталонный nsz сам распаковать корректно не может.
   Байт-эталона для полного XCI **нет**. Мы детектим его (`Xci.isFullXci()`: нет
   `HEAD` на 0x100 → заголовок на 0x1000) и читаем корректно, но вывод не с чем
   сверять — **требует реального сэмпла** перед обещаниями в релизе.
**Решение/где:** [hfs0.c](../app/src/main/cpp/hfs0.c) `hfs0_write_header`,
[ncz_engine.c](../app/src/main/cpp/ncz_engine.c) `ncz_convert_xcz_to_xci`. Подробно —
[architecture.md](architecture.md) A11.
**Как заметить:** выход XCI не совпадает с эталоном по размеру → проверь, что заголовок
раздела = 0x8000 и `0x200..0xF000` занулён. Для full XCI — лог `treating as full XCI`.

## G07: XCZ→XCI падает на XCI с пустым разделом (`file_count == 0`)
**Симптом:** XCZ→XCI обрывается на парсинге раздела: лог `Partition 'update' parse
failed: hfs0_parse: file_count 0 out of range`, затем `Invalid PFS0 container`, а
готовый вывод удаляется.
**Корень:** XCI-картриджи штатно содержат **пустой** раздел `update` (`file_count == 0`).
`hfs0_parse` отвергал `file_count == 0` как out-of-range. Плюс `calloc(0, …)` может
вернуть NULL — просто снять проверку мало, нужно обойти calloc/fread при 0.
**Решение:** [hfs0.c](../app/src/main/cpp/hfs0.c) `hfs0_parse_stream` — разрешить 0,
аллокацию и чтение записей делать только при `file_count > 0` (дальше цикл идёт 0 раз,
`free(NULL)` безопасен). Пришло из PR #6 (manx98).
**Диагностика (на будущее):** file-лог `nsz_debug.log` тут бесполезен — `dbg_open`
открывает его на `"w"` (перезапись на каждый прогон), а десктоп-копия устаревает.
Помогли кнопка «Сохранить лог с экрана» (`nsz_screen_log.txt`) и `adb logcat`. Если
нативный лог «пустой/старый» — смотреть экранный лог и logcat, а не файл.

## G08: `Flow.catch` в batch-режиме маскирует сбой под «Готово»
**Симптом:** в режиме «файлы» упавший XCZ→XCI показывался зелёным «Готово», внизу
«Обработано 1 из 1», без текста ошибки. В режиме «папка» — корректно.
**Корень:** в `startBatchConversion` на flow висел `.catch { … Failed }`. `Flow.catch`
ловит исключение и **завершает поток штатно**, поэтому код после `collect` безусловно
ставил `FileStatus.Completed`, перезатирая `Failed`.
**Решение:** [MainViewModel.kt](../app/src/main/java/com/androNSZ/viewmodel/MainViewModel.kt)
`startBatchConversion` — убрать `.catch`, дать исключению уйти во внешний `try/catch`
(он ставит `Failed` и не доходит до `Completed`); финальный summary добавляет строку об
ошибках. Режим папки не затронут — там статусы идут через `FolderProcessor`.
**Как заметить:** файл в очереди «Готово», хотя в логе есть `ERROR` по нему.
